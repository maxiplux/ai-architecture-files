# Architectural Documentation Guide

## Thinking Like an Architect

This guide presents a comprehensive view of documentation and diagrams needed in software projects, organized by purpose, audience, and project lifecycle.

---

## The Architect's Documentation Philosophy

An architect serves as a bridge between business needs and technical implementation. Documentation exists to:

1. **Communicate decisions** — Why we chose this approach over alternatives
2. **Enable onboarding** — New team members should understand the system quickly
3. **Reduce tribal knowledge** — Critical information shouldn't live only in people's heads
4. **Support evolution** — Future changes require understanding current state
5. **Facilitate governance** — Compliance, audits, and reviews need evidence

> **Golden Rule:** Document decisions and rationale, not just the final state. Code shows *what*, documentation explains *why*.
